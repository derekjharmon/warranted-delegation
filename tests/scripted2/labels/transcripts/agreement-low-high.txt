**The function** is `agreement(codes1, codes2)` in `agree.py`. It takes two lists of codes, one per coder, and returns `(percent agreement on a 0–100 scale, κ)`. κ is unweighted, as Cohen (1960) defines it. Codes are compared exactly as written, so case and spacing count. It raises an error in three cases: the lists differ in length, there are no items, or κ is undefined because both coders gave every item the same single category.

For this run I dropped the blank rows in a one-off script. Reading the CSV, dropping blanks, the argparse interface, JSON output and the unittest tests are the next steps under the methods-kit conventions.

**Problems in your notes.** These are in `notes/readme-draft.md` and `notes/references.md`. I haven't changed either file.

T4 · CLAUDE'S REPLY:
Here's what I propose for each case. In all of them the tool writes nothing to stdout when it fails, so a downstream program never reads a half-finished result.

**1. A required column is missing**
- **Proposal:** stop with an error on stderr and exit 1. The message should name the missing columns and list the ones it found, e.g. `missing column(s): coder2; found: item, coder1, coder_2`.
- Column names must match exactly, including case (`Coder1` doesn't count as `coder1`). The tool won't guess at near-matches.
- Extra columns are ignored, so people can keep notes columns in their files.
- An empty file, or one with no header row, gets the same error.

**2. Only one category in the data**
There are two different situations here:
- **Both coders used the same single category for every item.** Agreement is 100%, but chance agreement is also 1, so κ is 0/0 and undefined. **Proposal:** still report percent agreement and the dropped count, set `"kappa": null` in the JSON, print a warning on stderr explaining why, and exit 0. Percent agreement is still a true and useful number. Making the whole run an error would throw it away, and reporting κ as 0 or 1 would be wrong.
- **One coder used a single category and the other used several.** κ is well defined here and comes out at exactly 0. **Proposal:** report it as is. It's a real result: knowing coder 1's codes tells you nothing about coder 2's. The function already handles this.

The function currently raises an error in the first situation. I'd change it to return `None` for κ so the reporting layer can decide what to show.

**3. Fewer than two rows left after dropping blanks**
- **Proposal:** stop with an error on stderr and exit 1. The message should give the counts, e.g. `only 1 row left to compare (5 read, 4 dropped for blank codes); need at least 2`. The counts tell the user whether the file was short or mostly blank.
- With zero rows, nothing can be computed.
- With one row, both statistics can technically be computed. Percent agreement is 0 or 100. κ is undefined if the two codes match and exactly 0 if they don't. Neither number tells you anything about agreement, so I'd refuse rather than print something that looks like a finding.
- This check runs before the single-category check, so a single matching row gets this error rather than the `null` κ from case 2.

**One question for you:** what counts as blank? I'd treat only an empty cell as blank. A cell containing just spaces would then be a code, which follows the project rule to never recode anything. But `" "` is almost certainly a mistake, so another option is to stop with an error that names the row. I'd lean toward the error. What would you like?

**Matching rule:** I set it at 1e-9, meaning the two κ values may differ by at most 0.000000001. The two programs also have to compare the same number of rows. Both compute the same formula in standard double precision, so their rounding differences are around 1e-16. A real mistake, such as losing a category, miscounting a row or applying a weighting, would show up far above 1e-9. In practice the differences came out as exactly 0.

**The two files I made up** each test something the example doesn't:
- **`five_categories.csv`** has five categories, and one of them, `Praise`, is used only by coder2. That catches two common mistakes: treating `Praise` and `praise` as the same code, and building a table that silently drops a category one coder never used. It also has one row blank for one coder and one blank for both.
- **`worse_than_chance.csv`** has the coders mostly disagreeing, so κ is negative.

I also worked both new files out by hand. That gives κ = 43/99 for the first and −22/41 for the second, which equal the values above.
