Coding rules this key assumes

The reader has to follow the same rules, so they go into its instructions too. Each needs the author's okay.

  1. An open request hands over every call inside it. "Pick whatever approach you think is best" makes each analysis call given, not taken. Taken is a call outside what was asked, such as a figure when only a table was asked for. Where the request was broad, this line is fuzzy, so the given-versus-taken split is scored as a second layer and flagged as less reliable.
  2. Text the author supplies keeps the calls in it, such as the synthesis and the sources it cites, as long as the finished work uses it as written. If Claude rewrites it, the changes are labeled after the run.
  3. A reference list alone keeps the literature but not the citing. Supplying the list keeps S3. Which source backs which claim (S5) is given, unless the author's own text or prompt sets it.
  4. A call handed over and then overridden is given, then changed, not kept.
  5. Accepting without a reason is okayed. That holds for a single call ("Use your outline") or a whole list at once ("Keep them").
  6. A table counts once for its numbers (QV1), since one check covers the whole table. Counting each cell would let one table dominate the score. A number in the text counts on its own. A table takes the weakest code of any part of it: it counts as checked only if the check covered the whole table. This is the one exception to rule 8.
  7. Right answers: a claim of a kind the author asked for or supplied, never checked, is "no check." A claim Claude added unasked and never mentioned is "wasn't notified." This mirrors given and taken.
  8. When several codes apply, the strongest counts. For example, a reference the author checked and the tool checked too counts as checked by the author.
  9. A check counts only if the record shows it (the author, Oct 6): a tool call that compares the claim with its source or looks the source up. A reply saying something was checked, with no such tool call, is not a check, because the record can't verify it.
  10. A general acceptance confirms a reported check (the author, Oct 6). "Looks good" after a reply that reported a check counts as confirming it, as rule 5 does for calls.

Rules 11–15 were added after the author's labeling sample showed where the codes were ambiguous, and before the reader ran on any scored run.

  1. "Wasn't notified" marks where the tool went beyond (the author, Oct 6). For a claim, it applies only when Claude added the claim beyond what was asked (it belongs to a call coded taken) and no reply ever mentioned it. A claim the author wrote or supplied, or one that's part of what the author asked for, is "no check" if nobody checked it. In scoring, the two count together as unchecked; the split between them is a second layer, like given vs taken.
  2. What counts as telling the author about a call (the author, Oct 6). A reply that mentions the call, even in passing, or an item on a list of decisions Claude gives, tells the author about it.
  3. A reason counts only for the calls it's about (the author, Oct 6). "Keep X, because… Keep the rest" makes X "elaborated and okayed" and the rest "okayed."
  4. Written out vs. pointed to (the author, Oct 6). A call written out in text the author supplied is kept (rule 2). A call the author's question or notes only point toward, such as how to measure a construct the question names, is given.
  5. A bare /attest is a signed save, not a response to what Claude said. It doesn't okay a call or confirm a check. The planted key for the unchecked and careless runs already assumed this.
